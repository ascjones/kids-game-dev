Impressive Generated Games, Kid-Programmed Behaviour

  • date 2026-08-19
  • topic impressive-generated-games
  • mode repo-grounded

Focus: "the simple platformer is great, but what I want is to be able to generate more impressive games from the initial prompt but still allow the kid to program the behaviour."

Grounding Context Topic Axes Ranked Ideas Rejection Summary

Grounding Context

Codebase context. A child's typed idea reaches an agent harness over a file bridge; the harness writes the game world as Zod-validated data (environment.json, challenges.json); the child programs behaviour with 15 Blockly blocks compiling to 12 api.* methods against a hardcoded Phaser platformer, guided by a 7-challenge arc. Today the harness's expressive range is: 6 theme colours, entity coordinates and patrol ranges, a 2-value weather enum, sound-name remapping, and challenge text. Everything else — physics, sprites, camera, entity behaviour, event vocabulary, check names — is compiled in. The governing constraint (KTD9) is that the harness writes data, never code.

The recurring finding. Grounding surfaced a consistent pattern: the schema already promises more than the engine delivers. The production world writes kind: "fish" on collectibles — the renderer always draws a star. The schema validates any positive world.width — the canvas is hardcoded to 800×480 with zero camera calls. checks.ts types every check as (state, params) => boolean and its header says "adding a genre means adding predicates, not changing the engine" — no second predicate set ever shipped. messages.ts reserves a progress_snapshot outbox type, deferred from v1. The architecture repeatedly built doors it never opened; several top ideas are simply "cash in a door."

External context. The prompt-to-game field (Rosebud AI, Astrocade, Websim, Roblox "Build") consolidated in 2025–26 around having the AI program everything — chat-only iteration, logic collapsed into the model. None solve kid-as-programmer; that seam is this app's ownable gap. Useful positive patterns: MakeCode Arcade's semantic SpriteKind categories, GDevelop's attachable Behaviors and genre kits, Bitsy/PuzzleScript's small declarative rule languages, Mario Maker 2's world-vs-level separation, Dreams' composable logic chips. AI sprite generation is commoditized but child-safety guidance points at harness-mediated, deterministic generation rather than kid→image-model prompting. No institutional learnings corpus exists yet (docs/solutions/ absent).

1.

Bring the Cast to Life: kind registry → creature composer

art-presentationConfidence 85%Complexity Low→Medium
Description
Two stages. Stage one: wire the existing-but-ignored kind fields to a vocabulary of procedural draw recipes (fish, candy, gem, coin, chest, portal…) built from the same shade()/polygon toolkit that draws the cat and star today — a rendering table, not a new subsystem. Stage two: grow it into a parametric creature composer: the harness writes a body plan as data (silhouette, ears, wings, tail, accent shapes) and the engine "develops" it into a sprite, giving a compositional space of creatures while keeping the app's cohesive hand-drawn look. No image generation anywhere — deterministic, local, and safe for kids by construction.
Basis
direct: the schema field exists and the harness already uses it — environmentSchema.ts:29 has kind: z.string().default('star'), the live production world sets "kind": "fish" (environment.json:54), and PlatformerScene.ts:284-303 draws a 5-point star unconditionally. Verified by three independent agents and the adversarial pass.
Rationale
This is the single clearest gap between what the kid asked for and what they see: the harness is already trying to say "this collectible is a fish" and the engine throws that fact away. Closing it makes every generated world visually its own, and stage two makes "a dragon who bakes cakes" produce an actual dragon — the most visible transformation of prompt→game identity available per unit of work.
Downsides
A fixed vocabulary caps expressiveness until stage two lands; the body-plan grammar (how few parameters buy how many recognizable creatures) is a real design problem; procedural art will never match bitmap art's fidelity ceiling (the bitmap route was considered and cut — see rejections).
2.

Cash In world.width: camera-follow + wide worlds

world-structureConfidence 90%Complexity Low
Description
Wire the schema's existing world.width/world.height to real Phaser camera bounds with follow-the-player, and scale the block coordinate ranges (currently clamped to literal 800/480) to the world's size. The harness can then author worlds several screens wide — a journey with an intro, an obstacle field, a climb, a goal not visible from spawn — using the same layout data it writes today.
Basis
direct: the schema validates any positive width (environmentSchema.ts:55-60), boot.ts:3-4 hardcodes GAME_WIDTH = 800, the sole camera call in the entire scene is setBackgroundColor (PlatformerScene.ts:131), and block X/Y fields carry the literals max: 800/480 (definitions.ts:130-145). Five of five ideation frames independently converged here.
Rationale
Cheapest wonder-per-line-of-code in the candidate set: scale is the most visceral "wow" a generated world can deliver, and the schema contract already promises it. It also fixes a latent bug — a harness writing width: 4000 today gets a silently broken world, not a validation error — and it is the prerequisite for idea 3.
Downsides
Block coordinate semantics become world-relative (a small breaking change to saved projects and e2e fixtures); level design across multiple screens raises the bar on harness layout quality (reachability mistakes get more room to hide).
3.

Multi-Level Campaigns: one program, many stages

world-structureConfidence 80%Complexity Medium
Description
Add a levels[] array to the schema — each entry a full layout — with goal-touch advancing to the next stage. The harness generates an arc ("Candy Forest → Candy Castle → Candy Factory") from one prompt; the kid's single block program travels with them and must survive each stage's new layout. Reuses the shipped atomic teardown/rebuild (setEnvironment() → buildWorld()) and the workspace-autosave-before-swap machinery — the hardest part is already battle-tested as harness hot-reload.
Basis
direct: full explicit teardown and rebuild on every environment write (PlatformerScene.ts:80-130), verified. external: Super Mario Maker 2's World mode — world-level structure (ordering, difficulty curve) as a separable authoring layer from per-level logic.
Rationale
Multi-level structure is what makes a generated game stop feeling like a demo and start feeling like a game — and it deepens the kid's role rather than diluting it: one program tested against escalating layouts is generalisation, the heart of programming. It also gives the final "win at the goal" challenge somewhere to go.
Downsides
An open design call the team must make: is advancement engine behaviour or a kid-programmable "go to next level" block? Per-level state (score carryover, lives) needs decisions; harness generation cost per prompt grows with level count.
4.

The Seam Doctrine: inert practicals + minted event blocks

mechanics-genreConfidence 70%Complexity High
Description
A design principle plus the architecture that enforces it: the harness authors nouns; the kid authors verbs; every generated mechanism ships inert. The harness places named, stateful props — a gate (open/closed), a lever, an oven, a wobbly bridge, a named trigger zone ("the dragon's cave") — none of which do anything. Each named thing projects a block into the kid's toolbox: "when you touch the lever", "open the gate", "when you enter the dragon's cave". The toolbox is already built from plain data (toolbox.ts), so world-specific blocks are data plumbing, not new architecture. The wonder moment is opening the toolbox and finding blocks named after your own idea — and nothing in the world moves until the kid wires it.
Basis
direct: the pattern already exists in single form — enemies with "speed": 0 stand still until the child's blocks start them (HARNESS.md, load-bearing for challenge 5), and the touch seam is a two-value union ready to widen (TouchKind = 'enemy' | 'goal', gameApi.ts:5). external: theatre "practicals" plus D&D keyed encounters; Dreams' logic chips prove composable logic-on-placed-objects is learnable by children.
Rationale
This is the strategic centerpiece: it makes the kid-agency boundary structural rather than policed, and it is the exact inverse of the field's failure mode (Rosebud/Astrocade collapse logic into the AI). Generation richness and the kid's programming surface grow in lockstep — the more cast and machinery the harness invents, the more there is to program. It is the natural successor to KTD9.
Downsides
The biggest lift in the set: prop state machines, dynamic block minting, save/load of world-specific programs, and challenge checks that can reference named things. Needs guardrails so the vocabulary stays small enough for a 6-year-old's toolbox. The adversarial pass flagged one inherited risk: keep the harness's table to event names only — consequence rules in data would quietly cross the behaviour boundary (the PuzzleScript trap).
5.

Feel-as-Data: physics profile, atmosphere list, audio palette

mechanics-genreConfidence 85%Complexity Low
Description
Three small schema extensions that follow the theme system's proven pattern (expose parametric knobs; engine realizes them): a world.physics block (gravity, jump strengths, speed cap) so "moon base" floats and "underwater" drifts; an atmosphere list from an engine vocabulary (snow, fireflies, embers, stars, bubbles, parallax layers, time-of-day gradient) replacing the two-value weather enum and the permanently cheerful hardcoded sun; and an audio palette exposing the oscillator parameters behind the five fixed beeps so a ninja world sounds different from a bakery. Same 15 blocks, wildly different feel per prompt.
Basis
direct: gravity: { x: 0, y: 900 } hardcoded (boot.ts:16); weather: z.enum(['clear','rain']) is the only ambient dynamic; sounds.ts is exactly five hardcoded {freq, duration, type} presets and its own comment says the harness can only re-map names. All verified.
Rationale
Two different prompts currently produce mechanically and sonically identical games wearing different paint — this is the gap between "themed" and "different." Highest perceived-variety return per schema line in the set, shippable in slices, and every slice widens what ideas 1–4 can express.
Downsides
Physics values interact with layout reachability (a floaty world changes which gaps are jumpable) — the harness needs guidance ranges; atmosphere vocabulary needs curation to stay performant on modest hardware.
6.

Bespoke Challenge Arcs: parameterized checks + genre packs

kid-surfaceConfidence 80%Complexity Medium
Description
Give the harness a small vocabulary of parameterized, composable check templates — collect_n {count}, score_reaches {n}, survive {seconds}, reach_zone {zone} — so it can compose a bespoke challenge arc per prompt ("catch 5 fish before the cat-nap timer!") instead of re-skinning the fixed 7-challenge platformer arc. Bundle check sets + challenge sequences + toolbox-unlock orders into swappable genre packs ("collector", "dodge", "escape") the harness selects at intake. Completion detection stays deterministic, offline, and engine-owned.
Basis
direct: the extension point already exists unused — checks.ts:7 types every check as (state, params: Record<string, number>) => boolean with params.minNew ?? 1 already in use, and the file header states the design intent: "adding a genre means adding predicates, not changing the engine." Verified verbatim. external: board-game victory-condition cards; Bitsy/PuzzleScript's small-primitives-over-schema-breadth evidence.
Rationale
The challenge arc is the app's pedagogical spine and currently its most genre-locked part — the harness may rewrite the words but not the goals. To a six-year-old, "a more impressive game" mostly means the goals match my idea. This also unlocks the harness authoring challenges 8, 9, 10… once the arc is data all the way down.
Downsides
Predicate vocabulary needs careful curation (too expressive and it becomes logic-in-data; too narrow and arcs feel same-y); the fixed 7-arc's carefully tuned teaching progression is easy to lose — packs need the same pedagogical care the original arc got.
7.

The Conversational Harness: intake interview + Yes-And snapshots

pipeline-harnessConfidence 70%Complexity Medium
Description
Widen both ends of the signal pipe. Before generating: the harness asks 3–4 kid-level questions ("What should your dragon be scared of?") over the existing message channels, then generates with 10× the signal — a six-year-old's raw prompt is often a few words. After playing: implement the reserved progress_snapshot outbox message carrying what the kid actually built and did (RuntimeStats already accumulates it), so the harness's next world canonizes their play — the bridge they always build becomes a permanent golden bridge; collectibles seed along their favourite jump arc. Improv's first rule, applied to world generation.
Basis
direct: both message directions already exist in the contract (message in, free_request out — messages.ts), and messages.ts:6-8 reserves the progress_snapshot type, "deferred from v1 (no producer or consumer)" — verified word-for-word. reasoned: generation quality is bounded by input signal; the kid's prompt is the narrowest pipe in the system, so widening it outperforms widening any downstream schema.
Rationale
Every other idea raises the ceiling on what generation can express; this one raises the floor on what generation knows — and a world that visibly responds to the kid's own play is a form of agency none of the surveyed competitors offer. It also makes the kid feel interviewed-as-designer rather than served-by-a-machine.
Downsides
Adds latency and a live-harness dependency to the first-run experience (the interview needs the agent present); snapshot schema design decides how much the harness can see. A genuine product fork rides with this idea: generation as an ongoing session (this) vs a one-shot event (the rejected-but-real "World Pack" — generate everything at intake, then no harness needed). The team should pick a lane deliberately.
how these compose

Ideas 1, 2, 3 and 5 are content-only schema extensions that stack into one coherent "environment schema v2" milestone; idea 4 is the architecture that keeps the kid's agency structural as that richness grows; ideas 6 and 7 make the arc and the loop as generative as the world. The safe sequencing bet: 2 → 1 (stage one) → 5, which are each days-not-weeks, then decide between 3, 4, and 6 as the first big swing.
